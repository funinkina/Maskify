\chapter{System Design and Methodology}

\section{System Architecture Overview}

RE-DACT is designed as a small web application around a document-processing pipeline. The user uploads a PDF or image, selects a redaction level, optionally enables NER, and receives a redacted output file when the system finds PII.

The system has three main layers. The presentation layer is the browser interface in the \texttt{static} directory. It handles file selection, redaction-level selection, NER enablement, progress display, detection summaries, preview, and download. The API layer is implemented in \texttt{app.py} using FastAPI. It validates uploaded files, creates a temporary working directory, calls the redaction pipeline, stores downloadable results for a short time, and writes audit entries. The processing layer is split across \texttt{redaction.py}, \texttt{detectors.py}, \texttt{ner\_detector.py}, and \texttt{audit.py}.

The pipeline has six practical stages:

\begin{enumerate}
    \item File ingestion and extension validation.
    \item PDF-to-image conversion at 300 DPI for PDF inputs.
    \item OCR through Tesseract using multiple orientations and preprocessing states.
    \item PII detection through checksum validation, structural matching, regex, and optional NER.
    \item Character-level masking using OCR bounding boxes.
    \item Output assembly and audit logging.
\end{enumerate}

The implementation favors simple, inspectable components. Aadhaar and payment card validation are pure Python functions. Image rotation and masking use OpenCV. PDF conversion uses \texttt{pdf2image}, and PDF assembly uses \texttt{img2pdf}. The browser interface uses plain HTML, CSS, and JavaScript rather than a frontend framework.

The application uses temporary directories for uploaded and processed files. When redaction succeeds, the result is stored in an in-memory dictionary and remains downloadable for ten minutes. The cleanup routine removes expired working directories during later upload requests. This is a short-retention design. It avoids permanent document storage, but it does not mean the document exists only in memory.

\section{PII Detection Module Design}

The detection module is implemented in \texttt{detectors.py}. Each detector accepts a text string and returns a list of dictionaries with a common structure: type, value, start index, end index, length, and confidence. This shared output format lets the masking code treat detections consistently.

The rule-based detectors cover five PII types:

\begin{enumerate}
    \item Aadhaar numbers, validated with Verhoeff checksum.
    \item Payment card numbers, validated with Luhn checksum.
    \item PAN numbers, validated through structure and fourth-character holder type.
    \item Email addresses, detected with regex.
    \item Indian phone-number-like strings, detected with regex.
\end{enumerate}

The optional NER detector adds two more categories: names and address/location-like text. It uses the Hugging Face \texttt{dslim/bert-base-NER} model when \texttt{transformers} and \texttt{torch} are installed. If these dependencies are missing, the system continues with rule-based detection only.

Detection begins with candidate extraction. For Aadhaar and payment cards, the system searches for continuous digit sequences. For PAN, it searches for the official alphanumeric structure. The current implementation does not normalize spaced or dashed Aadhaar/PAN strings before detection, so such formats are a limitation. Candidate strings then pass through the relevant validation check before being reported.

After all detectors run, the module removes overlapping detections. It sorts detections by start position. If a new detection overlaps the most recently retained detection, the one with higher confidence is kept. If confidence is equal, the longer detection is kept. This rule is simple and predictable, but it also means a longer payment-card detection can replace a shorter overlapping Aadhaar detection when both have the same confidence.

\section{Verhoeff Algorithm for Aadhaar Validation}

The Aadhaar detector uses the Verhoeff algorithm. The algorithm processes digits from right to left and updates a checksum using two lookup tables: a multiplication table and a permutation table. If the final checksum is zero, the number passes validation.

In RE-DACT, \texttt{detect\_aadhaar} searches for 12-digit candidates, applies \texttt{verhoeff\_checksum}, and reports only candidates whose checksum is zero. It also rejects values ending in \texttt{1947}, a project-specific filter included to avoid one observed false-positive pattern.

\begin{algorithmic}[1]
\STATE \textbf{Input:} OCR text
\STATE \textbf{Output:} Aadhaar detections
\STATE Find all 12-digit candidate strings.
\FOR{each candidate $s$}
    \STATE $c \leftarrow \text{VerhoeffChecksum}(s)$
    \IF{$c = 0$ and $s$ does not end with 1947}
        \STATE Add an Aadhaar detection with confidence 1.0.
    \ENDIF
\ENDFOR
\STATE \textbf{return} detection list
\end{algorithmic}

The validation cost is negligible compared with OCR because Aadhaar has a fixed length of 12 digits.

\section{Luhn Algorithm for Payment Card Validation}

The payment card detector uses the Luhn algorithm. It scans digit sequences of 13--19 characters, doubles every second digit from the right, subtracts 9 from doubled digits above 9, and checks whether the final sum is divisible by 10.

\begin{algorithmic}[1]
\STATE \textbf{Input:} OCR text
\STATE \textbf{Output:} payment card detections
\STATE Find all 13--19 digit candidate strings.
\FOR{each candidate $s$}
    \IF{$\text{LuhnChecksum}(s)$ is true}
        \STATE Add a payment card detection with confidence 1.0.
    \ENDIF
\ENDFOR
\STATE \textbf{return} detection list
\end{algorithmic}

The Luhn check is not proof that a card is active or issued. It only confirms that the number follows a valid checksum pattern. This is still useful because it rejects many random digit sequences that regex alone would flag.

\section{PAN Card Detection with Entity Validation}

PAN numbers use a fixed ten-character structure. The first five characters are uppercase letters, the next four are digits, and the last character is an uppercase letter. The fourth character represents the holder type. RE-DACT checks the fourth character against the valid set \texttt{A, B, C, F, G, H, J, L, P, T}.

\begin{algorithmic}[1]
\STATE \textbf{Input:} OCR text
\STATE \textbf{Output:} PAN detections
\STATE Find candidates matching five letters, four digits, and one letter.
\FOR{each candidate $s$}
    \IF{the fourth character is a valid holder-type code}
        \STATE Add a PAN detection with confidence 1.0.
    \ENDIF
\ENDFOR
\STATE \textbf{return} detection list
\end{algorithmic}

This validation reduces false positives but does not prove that the PAN was issued by the Income Tax Department. It is a format and holder-type check, not an online verification step.

\section{Named Entity Recognition for Unstructured PII}

The optional NER module handles unstructured PII that cannot be validated with checksums. The implementation uses the \texttt{dslim/bert-base-NER} model through the Hugging Face Transformers pipeline. It maps \texttt{PER} labels to \texttt{name} and \texttt{LOC} labels to \texttt{address} in the internal output.

The module first checks whether \texttt{transformers} and \texttt{torch} can be imported. If not, it returns an empty list and the rest of the system continues normally. When the dependencies are present, the FastAPI startup event preloads the model to avoid first-request latency.

The NER function processes long OCR strings in 512-character chunks with a 50-character overlap. This is a practical implementation detail in the current code; it is not token-aware chunking. Each returned entity is filtered by confidence threshold, defaulting to 0.85. Duplicate spans created by overlapping chunks are skipped.

NER improves coverage for names and locations, but it has clear limits. The model was trained on English news text, not Indian identity cards or OCR output. It may miss address fragments, mislabel organizations, or behave poorly on noisy scans. For this reason, the report treats NER as an optional extension rather than the main basis for redaction.

\section{Multi-Orientation OCR Pipeline}

The multi-orientation OCR pipeline is implemented in \texttt{Extract\_and\_Mask\_UIDs}. It exists because scanned documents are often rotated. A single OCR pass may fail if the text is sideways or upside down.

For each image, the system converts the input to grayscale and prepares eight variants:

\begin{enumerate}
    \item original orientation,
    \item 90 degrees counterclockwise,
    \item 180 degrees,
    \item 90 degrees clockwise,
    \item blurred original,
    \item blurred 90 degrees counterclockwise,
    \item blurred 180 degrees,
    \item blurred 90 degrees clockwise.
\end{enumerate}

The blur uses a $5 \times 5$ Gaussian kernel. Tesseract runs with English OCR, OCR engine mode 3, and page segmentation mode 11 for sparse text. After each OCR attempt, the system reconstructs text from character bounding boxes and runs the PII detectors.

The pipeline stops at the first variant that produces at least one detection. This early exit keeps correctly oriented documents fast. If none of the eight variants produces a detection, the function returns no masked output for that image.

\begin{algorithmic}[1]
\STATE \textbf{Input:} image path and redaction level
\STATE \textbf{Output:} masked image path and detections
\STATE Convert image to grayscale.
\STATE Build eight orientation/preprocessing variants.
\FOR{each variant}
    \STATE Extract character boxes with Tesseract.
    \STATE Reconstruct text from OCR boxes.
    \STATE Run PII detection.
    \IF{one or more detections are found}
        \STATE Mask the selected character boxes on the image.
        \STATE Return the masked image path and detections.
    \ENDIF
\ENDFOR
\STATE \textbf{return} no output and an empty detection list
\end{algorithmic}

\section{Masking Strategies and Implementation}

The masking logic is controlled by \texttt{get\_mask\_range}. It returns the range of characters to hide inside each detected value.

For structured identifiers, the current behavior is:

\begin{enumerate}
    \item Standard: mask all characters except the last four.
    \item Partial: mask the first four characters only.
    \item Full: mask every character.
\end{enumerate}

For names, locations, email addresses, and phone numbers, the implementation always returns the full range. This prevents partial disclosure of values that do not have a safe or useful fixed reveal pattern.

Masking happens at the character level. Tesseract returns one bounding box per recognized character. For each character selected for masking, OpenCV draws a filled black rectangle over the corresponding box. If OCR was performed on a rotated version of the image, the code rotates the image before masking and rotates it back afterward, so the final output matches the original orientation.

For PDFs, each page is converted to an image and processed separately. Pages with detections are replaced by masked images. Pages without detections are kept as converted page images. If at least one page is redacted, \texttt{img2pdf} combines the pages into a new output PDF.

\section{Overlap Deduplication Logic}

Overlap deduplication prevents the system from reporting the same character span multiple times. This can happen when a digit sequence is matched by more than one detector or when NER overlaps with a regex detection.

The algorithm sorts all detections by start index. It then compares each detection with the last retained detection. If the two spans overlap, the higher-confidence detection is retained. If both have the same confidence, the longer span is retained. Adjacent spans are not considered overlapping.

This rule is intentionally simple. It avoids complicated priority tables and gives deterministic output. A future version could add explicit detector priorities, for example preferring Aadhaar over payment card when a valid Aadhaar is embedded in a longer digit sequence.

\section{Tamper-Evident Audit Logging}

The audit module writes one JSON object per line to \texttt{audit.log} by default, or to the path set in \texttt{AUDIT\_LOG\_PATH}. Each entry records timestamp, request ID, filename, file type, redaction level, detection counts, pages processed, processing time, action, previous hash, and entry hash.

The hash chain works by storing the previous entry's hash in \texttt{prev\_hash}. The current entry is serialized with sorted keys before the \texttt{hash} field is added, and SHA-256 is computed over that canonical JSON string. The resulting hash is then written into the entry.

This design makes later edits detectable if the log is verified in sequence. However, the current implementation keeps the previous hash only in process memory and initializes it to 64 zero characters when the application starts. That means the chain is continuous during a running process, but a production version should read the last existing log entry during startup if it needs an uninterrupted chain across restarts.

Concurrent writes are protected by a threading lock. The audit log stores metadata and detection counts, not the file contents or raw detected values.

\section{System Interfaces and API Design}

The REST API exposes three endpoints.

\texttt{GET /api/health} returns application status, version, and whether NER dependencies are available.

\texttt{POST /api/process-file} accepts multipart form data. It requires a file and accepts optional fields for \texttt{level}, \texttt{use\_ner}, and \texttt{confidence\_threshold}. Supported file extensions are PDF, JPG, JPEG, and PNG. Valid redaction levels are \texttt{standard}, \texttt{partial}, and \texttt{full}. Unsupported file types or invalid levels return HTTP 400 errors.

\texttt{GET /api/result/\{request\_id\}} returns the processed file if the result still exists and has not expired. If the result is missing or older than the ten-minute TTL, the endpoint returns HTTP 404.

The browser interface uses these endpoints directly. It shows total detections, pages processed, processing time, selected redaction level, file type, a detection-type breakdown, a detections table, a preview, and a download link when a redacted file is available.

\section{Summary}

The RE-DACT design combines simple pieces: OCR, validation checks, optional NER, character-level masking, temporary result storage, and hash-linked audit entries. The strongest part of the system is structured identifier handling, where Verhoeff and Luhn validation reduce false positives. The more uncertain parts are OCR quality and NER-based unstructured detection, which depend heavily on input quality and model fit.

The next chapter explains how this design is implemented, tested, and evaluated in the working application.
